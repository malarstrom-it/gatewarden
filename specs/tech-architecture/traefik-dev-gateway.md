# Traefik Dev Gateway — architecture plan (under review)

Status: **plan only**. Nothing in this document is implemented. Every technical claim that
carries a decision is backed by an official source; the citation table and the verdicts live in
[`grill-findings.md`](./grill-findings.md).

Traefik documentation cited below is the current docs set served at
`https://doc.traefik.io/traefik/reference/...` (the docs describe **Traefik v3.7**). Note that the
older `docs.traefik.io` alias is only partly usable: `docs.traefik.io/traefik/<path>` redirects to
`doc.traefik.io/traefik/traefik/<path>`, which 404s for some pages, so citations use the
canonical `doc.traefik.io` paths that were actually fetched.

## 1. Problem statement

This container runs AI coding agents. Each project an agent creates runs its dev server on
`127.0.0.1:PORT` **inside this container**. The user sits on the same network as the host machine
that runs this container and cannot reach those ports: from the user's laptop the dev servers are
invisible.

The goal is a gateway that

1. lets the user **click a URL** and reach the dev server an agent is running,
2. lets a project **register and withdraw** its dev server **at runtime**, independently of the
   other projects (atomic registrations),
3. gives the user an **overview of everything the agents currently run**.

### 1.1 Namespace requirement (from the user)

Namespaces must be **semantic and atomic**:

```
<branch>.<project>.<zone>
```

* the **branch** is the leading label, so a branch-scoped dev lifecycle is visible in the URL,
* every **project** owns a distinct prefix label,
* the trailing **zone** is the user's own wildcard DNS suffix (still unconfirmed — the exact
  wildcard record is being asked for; the **position of the project label is a parameter**, not a
  hard-coded constant).

Examples with two different zones (both valid layouts of the same template):

| zone (user's wildcard) | resulting FQDN for branch `main`, project `alpha` |
| --- | --- |
| `example.test` | `main.alpha.example.test` |
| `apps.example.test` | `main.alpha.apps.example.test` |

The plan therefore never hard-codes a label count. It uses a template
`fqdn_template = "{branch}.{project}.{zone}"` with `{branch}`, `{project}` and `{zone}` slots; a
different zone changes only the `{zone}` value.

**Consequences (these drive every choice below):**

* This container **cannot be re-created from inside** (no socket, no Docker CLI). Anything that
  requires new published ports on *this* container is a **host-side task for the user**.
* This container **is** attached to a user-defined Docker network, so a second container joined to
  that network can reach this container **by container name or IP**.
* A dev server bound to `127.0.0.1` inside this container is **not** reachable from another
  container — loopback is per-container.

## 3. Candidate architectures

### Candidate A — Traefik runs inside this container

**Idea.** Install Traefik in this container; it proxies straight to `127.0.0.1:PORT`.

**Verdict: ruled out for now; it is a host-side task.**

* The user reaches Traefik through the **host's** published port. Publishing is a create-time
  property of a container: Docker docs — "Published container ports are mapped to host IP
  addresses." and "Use the `--publish` or `-p` flag to make a port available outside the host, and
  to containers in other bridge networks." Ports published to loopback are LAN-invisible: "If you
  include the localhost IP address (127.0.0.1, or ::1) with the publish flag, only the Docker host
  can access the published container port."
* Re-creating this container to add `-p 80:80 -p 443:443` **cannot be done from inside** (no
  socket, no CLI). It requires the user to re-create the container on the host.
* Also note: publishing to `0.0.0.0` matters — "In nat mode network, publishing a port to an
  address on the loopback interface means remote hosts cannot access it."
* No `traefik` binary is present; nothing may be installed by this task.

*If the user prefers A*, the host must: re-create this container with published ports and a
shared configuration path, and Traefik must be run inside it (binary or sidecar-in-the-same-namespace).

### Candidate B — Traefik as a separate container on the same user-defined network  ← **recommended**

**Idea.** The host creates a second container (`traefik:v3.7`) on the **same user-defined network**,
publishes `80`/`443` on it, and it proxies to this container's dev servers.

* Traefik reaches this container by name or IP: Docker docs — "Once connected to a user-defined
  network, containers can communicate with each other using container IP addresses or container
  names."
* The user reaches Traefik through the host's published ports — the host creates that container, so
  publishing works and this container never has to be re-created.
* **Loopback caveat (decisive):** a dev server bound to `127.0.0.1` inside this container is
  invisible to Traefik in another container. Two ways out, both documented/derived from Docker's
  own behaviour:
  * **(B1) rebind:** dev servers listen on `0.0.0.0` inside this container; Traefik targets
    `http://<this-container-ip>:<port>`. Simple, no extra process.
  * **(B2) relay:** a small forwarder inside this container listens on `0.0.0.0:<relay-port>` and
    forwards to `127.0.0.1:<dev-port>`; Traefik targets the relay port. Keeps agent frameworks on
    their default loopback bind. Docker's own docs demonstrate the namespace-sharing trick that
    makes this possible: "The following example runs a Redis container, with Redis binding to
    127.0.0.1, then running the `redis-cli` command and connecting to the Redis server over
    127.0.0.1." — with `--network container:redis`, i.e. the second container joins the first
    container's network namespace and therefore shares its loopback.
* Traefik's own ports: the documented quick start publishes `"80:80"` and `"8080:8080"` with image
  `traefik:v3.7`; the Helm chart defaults are "the entryPoints web (port 80), websecure (port 443),
  traefik (port 8080) and metrics (port 9100)".

### Candidate C — Traefik on the host with the Docker provider

**Idea.** Run Traefik on the host with `providers.docker`, let it discover containers by label.

**Verdict: ruled out for the dev-server routing job.**

* The Docker provider can only route to **containers**: "Traefik retrieves the private IP and port
  of containers from the Docker API." and "Traefik requires access to the docker socket to get its
  dynamic configuration."
* The dev servers here are **plain processes inside one container**, not containers, so they carry
  no `traefik.*` labels and never appear in the Docker API.
* The provider *does* reach unpublished container ports (it uses the container's private IP and
  port), so it is not the "published ports" that break it — the absence of labelled containers is.
* It would only become viable if the architecture changed so every dev server runs in its own
  labelled container — a much larger change than the problem asks for.
* Useful anyway: the provider's defaults are a security lesson for any design that uses it —
  `providers.docker.exposedByDefault` defaults to **true** ("Expose containers by default through
  Traefik"), which would publish every container on the network.

## 4. How dynamic configuration reaches Traefik

| Option | Mechanism | Fits this topology? |
| --- | --- | --- |
| **File provider** | `providers.file.directory` — "Defines the path to the directory that contains the configuration files. The filename and directory options are mutually exclusive. It is recommended to use `directory`." `providers.file.watch` defaults to `true` | Needs a **shared path** between this container and the Traefik container ⇒ host-side bind/volume. Documented caveat: "With the file provider, Traefik listens for file system notifications to update the dynamic configuration. If you use a mounted/bound file system in your orchestrator (like docker or kubernetes), the way the files are linked may be a source of issue." |
| **HTTP provider** | `providers.http.endpoint` — "Defines the HTTP(S) endpoint to poll." (required); `providers.http.pollInterval` default `5s`; `providers.http.pollTimeout` default `5s`; `providers.http.headers` default `{}`; TLS via `providers.http.tls.ca` / `providers.http.tls.insecureSkipVerify` (default `false`) | **Fits.** This container is already reachable by the Traefik container on the shared user-defined network. No shared mount needed. Costs: poll latency (tunable), and one aggregator that owns the document. Bonus: `headers` carries a shared secret, so the config endpoint can be authorized. |
| **Docker labels** | `traefik.http.routers.*.rule` etc. | Ruled out — see Candidate C. |
| **Traefik API (`api@traefik.io`)** | `api`, `api.dashboard`, `api.insecure` | **Not a configuration delivery channel.** The API is read-only for dynamic configuration: "All the following endpoints must be accessed with a GET HTTP request." The documented ways to supply routing configuration are file, labels, annotations, KV and tags. `api@traefik.io` is for *observing* configuration (dashboard, `/api/http/routers`, `/api/http/services`, `/api/rawdata`), not for injecting it. |

**Recommendation: HTTP provider, file provider as the alternative.**
The HTTP provider is immune to the documented fsnotify/mounted-filesystem caveat of the file
provider, needs no shared volume (the host only has to create one container), and gives a single
place to authorize registrations (`providers.http.headers`). The file provider remains attractive
because one file per registration is the most literal form of "atomic" (add = write one file,
remove = delete one file) — it is the better fit if the host prefers a shared Docker volume and
accepts the documented mount caveat.

## 5. Registration model (atomic, project-scoped, branch-scoped)

A **registration** is one small record, owned by one project, for one branch, on one port:

```yaml
project: alpha          # project prefix label (unique per project)
branch: feature/login   # branch name (sanitised, see below)
port: 5173              # port the dev server listens on inside this container
fqdn: feature-login.alpha.example.test   # derived, not free-form
```

Derivation rules (all inputs are the record's own fields):

1. `project_slug` = sanitised project label (unique per project; the project claims one prefix).
2. `branch_slug` = sanitised branch name.
3. `fqdn` = `fqdn_template.format(branch=branch_slug, project=project_slug, zone=zone)`.
4. `rule` = `Host(`<fqdn>`)` — **exact**, one label set, no wildcard.
5. `service` = one service whose backend URL points at this container's IP and the registered port
   (or at the relay port of candidate B2): file-provider style
   `loadBalancer.servers[0].url = "http://<this-container-ip>:<port>"`.
6. Withdraw = delete that registration; nothing else changes.

### 5.1 One registration = one router = one service

* "If the rule is verified, the router becomes active, calls middlewares, and then forwards the
  request to the service." (router docs)
* "service — The name of the service that will handle the matched requests." (required field)

Hence **one router can only ever serve one backend**. Two registration strategies follow:

* **Exact-Host router per registration (recommended).** `Host(`feature-login.alpha.example.test`)`
  → one service → one port. Fully atomic: adding/removing one branch touches one router; every
  route shows up individually in `/api/http/routers` and in the dashboard.
* **Wildcard-per-project router (limited).** `Host(`*.alpha.example.test`)` matches *every* branch
  of that project — but since a router has exactly one service, it can only work if **all concurrent
  branches of that project share one backend port**. It is a valid optimisation only for a project
  that serves one dev server at a time on a fixed port. The docs are explicit that the wildcard
  matches one label: "A wildcard matches exactly one subdomain label: `*.example.com` matches
  `foo.example.com` but not `foo.bar.example.com` or `example.com` itself." — so
  `Host(`*.example.test`)` does **not** match `main.alpha.example.test` (two labels below the zone),
  but `Host(`*.alpha.example.test`)` **does** match `main.alpha.example.test`.
* **`HostRegexp`** only if a genuinely dynamic branch label must be matched; the docs state the
  `Host` matcher "should be preferred over the `HostRegexp` matcher as it allows attaching a TLS
  option and is more efficient."

### 5.2 Branch-name sanitisation (industry standard)

GitLab's `CI_COMMIT_REF_SLUG` is the well-known slug rule: "CI_COMMIT_REF_NAME in lowercase,
shortened to 63 bytes, and with everything except 0-9 and a-z replaced with `-`. No leading /
trailing `-`. Use in URLs, host names and domain names."
The plan adopts that rule for the branch label and the same rule for the project label.

### 5.3 Industry standard for the shape

The prevailing convention is **project-scoped, branch-qualified** hostnames. Vercel: "The URL
generated from a Git branch will always show you the most recent changes for the branch and won't
change if you push new commits to the branch." with URL structure
`<project-name>-git-<branch-name>-<scope-slug>.vercel.app`; commit URLs are
`<project-name>-<unique-hash>-<scope-slug>.vercel.app`.
The two dimensions match the user's request; the **ordering differs** — Vercel puts the project
first, the user wants the branch first. (GitLab review apps use the branch-first shape; the GitLab
review-apps page returned HTTP 403 to a plain fetch and is therefore **not** cited here. The
GitLab predefined-variables page, which was fetched, is cited for the slug rule only.)

For local-only names, RFC 2606 reserves: "`.test` is recommended for use in testing of current or
new DNS related code. `.example` is recommended for use in documentation or as examples. ...
The `.localhost` TLD has traditionally been statically defined in host DNS implementations as
having an A record pointing to the loop back IP address and is reserved for such use."

## 6. DNS side: the wildcard record

The user's own DNS holds a wildcard record for the zone. DNS wildcards and Traefik wildcards do
**not** behave the same way — this asymmetry is the single most important fact in the plan.

* **DNS wildcards match at any depth.** RFC 1034 §4.3.3: "The owner name of the wildcard RRs is of
  the form `*.<anydomain>`, where `<anydomain>` is any domain name. ... The wildcards potentially
  apply to descendants of `<anydomain>`, but not to `<anydomain>` itself." and "Another way to look
  at this is that the `*` label always matches at least one whole label and sometimes more, but
  always whole labels." RFC 4592 §2.2.1 walks the same example: a zone with `*.example.` answers
  `QNAME=foo.bar.example.` with the wildcard's data "because `bar.example.` does not exist, but the
  wildcard does."
  ⇒ **A single `*.<zone>` record can resolve `branch.project.zone`** — no per-project DNS record is
  needed — *provided* no closer name exists.
* **The caveat (must be stated):** RFC 1034 §4.3.3 — "Wildcard RRs do not apply: When the query is
  in another zone. That is, delegation cancels the wildcard defaults. When the query name or a name
  between the wildcard domain and the query name is known to exist." So if a concrete
  `project.zone` name ever exists in the zone, the `*.<zone>` wildcard stops covering
  `branch.project.zone`.
* **Traefik's `Host` wildcard matches exactly one label** — the quoted rule above. Traefik routing
  therefore never relies on wildcards in the recommended design: every route uses an exact
  `Host(...)` rule.
* **Consequence for the design:** the user's existing single wildcard record is (probably)
  sufficient; the gateway does not need to touch DNS. Only if the user wants a per-project
  wildcard (`*.project.zone`) would a per-project record be needed — and that is not required by
  this plan.

## 7. How the user sees everything the agents run

Two layers, both cheap:

1. **Traefik dashboard** — `api: true` enables it ("Enable api/dashboard. When set to true, its sub
   option api.dashboard is also set to true.", default `false`); `api.dashboard` default `true`;
   served at `/dashboard/` ("The dashboard is available by default on the path `/dashboard/`. Note:
   The trailing slash `/` in `/dashboard/` is mandatory."). `api.insecure: true` exposes it on the
   entryPoint named `traefik` — the docs' own quick start uses it, but warns: "Do not enable this
   flag in production."
2. **A gateway index page** — the registry inside this container knows every registration, so it
   can render the live list (project, branch, port, FQDN, link) itself. No scraping needed. The
   Traefik API is a good cross-check: `/api/http/routers` ("Lists all the HTTP routers
   information."), `/api/http/services`, `/api/overview`.

## 8. Security posture (proposal; the details are a user decision)

* **Never expose the API/dashboard blindly.** Docs: "Enabling the API and the dashboard in
  production is not recommended, because it will expose all configuration elements, including
  sensitive data, for which access should be reserved to administrators." and "It's recommended to
  NOT publicly exposing the API's port, keeping it restricted to internal networks."
* Bind the dashboard to an internal entryPoint or protect it with middlewares (`basicAuth`,
  `ipAllowList`) rather than `api.insecure` on a LAN-exposed port.
* The registry endpoint that serves the dynamic configuration is the **write side** of the
  gateway: whoever can reach it can publish routes. Protect it (network restriction + the shared
  secret carried in `providers.http.headers`).
* Only the Traefik container's published `80`/`443` should be reachable from the LAN; the
  registry's port stays on the Docker network.
* If the Docker provider is ever added: set `providers.docker.exposedByDefault: false`
  ("If set to false, containers that do not have a `traefik.enable=true` label are ignored") and
  remember "Accessing the Docker API without any restriction is a security concern".

## 10. Open decisions for the user

Only genuine trade-offs, each with options and a recommendation.

1. **Where Traefik runs.** (a) separate container on the same user-defined network — *recommended*;
   (b) inside this container, which requires the host to re-create this container with published
   ports; (c) on the host with the Docker provider — *ruled out* for dev-server routing.
2. **How dynamic configuration is delivered.** (a) HTTP provider with a registry inside this
   container — *recommended*; (b) file provider `directory` over a shared Docker volume, with the
   documented fsnotify-on-mounted-filesystem caveat.
3. **URL naming scheme.** (a) branch-first `{branch}.{project}.{zone}` — *recommended*, matches the
   user's stated requirement; (b) project-first `{project}.{branch}.{zone}`, matching Vercel's
   ordering. The zone value is the user's own wildcard and is still unconfirmed.
4. **How dev servers become reachable.** (a) rebind dev servers to `0.0.0.0` inside this container
   — *recommended*, no extra process; (b) run a relay in this container that forwards
   `0.0.0.0:<relay>` → `127.0.0.1:<dev-port>`, keeping agent frameworks on their default bind.
5. **Registration scope.** (a) per-project namespaced prefixes — *recommended*, matches the user's
   requirement and the industry shape; (b) one global flat namespace, simpler but no project
   ownership.
6. **Security posture.** (a) dashboard on an internal-only entryPoint, API protected by middlewares
   — *recommended*; (b) `api.insecure` on a LAN port (dev quick-start style, docs warn against
   production use); and whether the registry endpoint is open on the Docker network or requires a
   shared secret.
7. **TLS.** (a) plain HTTP on the LAN — *recommended for a first cut*; (b) HTTPS with a wildcard
   certificate covering the zone. Note the docs prefer exact `Host` rules partly because that
   matcher "allows attaching a TLS option"; wildcard-certificate handling for the TLS reference
   pages fetched here is **undocumented**, so (b) needs its own verification.

## 11. Out of scope

Implementation (no Traefik install, no containers, no compose files, no service scripts) waits for
the user to confirm the shared understanding in §10.
